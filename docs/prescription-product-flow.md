# 처방전 → 공식 제품 → 제형별 가이드

OCR 엔진, Google Vision 호출, bounding box/숫자 parser, local fallback 및 기존 prescription 테스트는 변경하지 않았다. `medicine-flow.js`는 OCR 결과 이후의 제품 매칭/분류 정책만 담당한다. 기존 MFDS endpoint, 서버 요청 파라미터, API key, cache와 Supabase schema도 그대로다.

## 매칭

기존 `/api/medicines`와 `/api/liquids`(허가정보 검색)를 이름으로 조회한 뒤 품목기준코드 `id`로 중복을 제거한다. 처방전 보험코드는 `insuranceCode`/EDI와만 비교하며 `item_seq`와 혼용하지 않는다.

우선순위: `exact-code` → `exact-name` → `high-confidence` → `needs-confirmation` / `not-found`.

유일한 코드 일치 또는 모든 조회가 완료된 경우의 유일한 정규화 이름 일치만 자동 선택한다. 동일 코드/이름에 여러 공식 품목이 있으면 선택하지 않는다. 알려진 보험코드 불일치를 이름으로 덮어쓰지 않는다. 이름 fuzzy는 숫자 함량 서명이 같고 문자 차이 1개·유사도 0.9 이상일 때의 후보 표시용이며 자동 선택하지 않는다.

비교용 이름은 공백, 내복 등 지정 부가표현, 포장단위, 비본질적 구두점, 영문 대소문자를 정리하고 mg/밀리그램을 통일한다. 숫자, 소수점과 복합 함량의 숫자 구분은 보존한다. OCR 원문은 변경하지 않는다. 검색어에서는 브랜드 구분 하이픈을 보존해 기존 prefix fallback을 계속 사용할 수 있게 했다.

각 API의 조회는 최대 3페이지로 제한한다. 미조회 페이지 또는 API 실패가 있으면 이름 일치만으로 자동 선택하지 않는다. 공식 후보 검색 실패는 OCR 목록을 삭제하지 않으며 재시도/직접 선택/인식 수정 기능을 유지한다.

## 분류와 공통 라우팅

`MedicineFlow.classifyMedicineForm`은 공식 제형 필드를 우선하고, 공식 성상과 제품명으로 보완한다. 비경구 액제는 경구 액체 가이드에서 제외한다. 오래된 낱알 식별 기록은 공식 형태/치수도 보조 단서로 사용한다.

`MedicineFlow.getMedicineDestination`과 `app.js:openMedicine`이 공통 목적지/CTA를 결정한다. `selectMedicine`은 선택 상태와 3D 입력을 쓰기 **전에** solid-oral 여부를 재확인한다. 일반 검색·처방 카드·처방 비교·저장·최근 조회가 같은 경로를 사용한다. 저장 비교는 solid-oral만 허용하며 과거의 잘못된 kind: pill만 믿지 않는다. other/unknown은 제품 정보/확인 dialog를 연다.

액체 포장은 pouch/bottle/other/unknown으로 분류한다. 혼합 포장은 unknown으로 유지한다. 기존 상단 기준 분할선 계산식은 변경하지 않았다. 병은 `applyContainerType`에서 pouch 강제 전환을 막고 기존 overlay의 pouch-only 가드를 유지한다. 공식 포장 유형을 알 수 없는 경우에는 기존 사용자 확인 절차를 사용한다.

공식 캡슐/정제 정보가 있으면 표시 단위를 보완한다. 포 제품의 숫자 투여량에는 포 단위를 사용할 수 있지만 명시적으로 읽힌 mL를 임의로 포로 변환하지 않는다. 병의 전체 포장 용량을 1회 투여량으로 환산하지 않는다.

## 저장과 UI

기존 localStorage `savedMedicinesV1` 항목의 metadata에 공식 제품명·보험코드·제조사·제형·medicineForm·liquidPackaging·처방 숫자/단위를 추가한다. 공식 코드가 없으면 productCode는 null이며 원래 인식 코드는 별도 recognizedProductCode로만 보관한다. 저장은 기존처럼 사용자의 저장 버튼으로만 수행한다. 원본 처방전 이미지와 전체 OCR 문장은 저장하지 않는다.

자동 선택 후 제형과 주 CTA를 먼저 표시하고 다른 후보는 접힌 영역에서 변경할 수 있다. 인식 수정 버튼은 유지한다. 매칭 전략은 `window.MEDICINE_DEBUG === true`인 개발 환경에서만 표시/로그한다.

## 실제 MFDS / 브라우저 확인

로컬 앱의 기존 MFDS API/cache를 사용해 다음 응답을 확인했다. 브라우저 검증 입력은 사용자가 제공한 정상 OCR 4행이며, 원본 사진을 다시 Google Vision으로 보내지는 않았다.

| OCR 이름 | 반환 공식 제품 | 품목기준코드 | 매칭 | 제형/목적지 |
|---|---|---|---|---|
| 듀파락-이지시럽 | 듀파락시럽(락툴로오즈액) | 201701391 | needs-confirmation, 코드 미제공·이름 다름 | 후보 liquid / pouch; 사용자 선택 후 액체약 가이드 |
| 에도스캡슐 | 에도스캡슐(에르도스테인) | 200402284 | exact-code: 649401610 | solid-oral / 실물크기 |
| 애니코프캡슐300mg | 애니코프캡슐300밀리그램(테오브로민) | 200805990 | exact-code: 650202970 | solid-oral / 실물크기 |
| 셀벡스캡슐(내복) | 셀벡스캡슐(테프레논) | 198800119 | exact-code: 642204150 | solid-oral / 실물크기 |

듀파락 후보의 공식 포장단위는 `포 - 20포/상자[15mL/포x20]`이며 성상은 시럽제/파우치를 명시했다. 같은 제품이라고 확정할 보험코드가 없으므로 강제 자동 매칭하지 않았다. 브라우저에서 후보 수동 선택 후 liquid 화면 진입, pill 숨김, pouch 가이드 연결을 확인했다.

## 제한

현재 API 계약에는 보험코드 검색 입력이 없으므로 이름으로 가져온 후보 내에서 EDI를 비교한다. 이름 검색으로 후보 자체를 가져오지 못하면 코드만으로 찾을 수 없다. 제형/코드가 없는 공식 응답, 브랜드 변경·성분명이 붙은 이름, 미조회 페이지는 사용자 확인이 남을 수 있다. 단일 코드 매칭 단위 테스트의 듀파락 fixture는 요구 조건 검증용 가상 공식 응답이며 위 실제 조회 결과와 구별한다.
